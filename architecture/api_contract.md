# LittleSteps - API Contract

## 1. Purpose

This document defines the V1 API contract between the LittleSteps mobile app and the NestJS backend.

It describes resource shapes, endpoint responsibilities, validation expectations, and media upload flow. It does not define controller implementation, database queries, or UI behavior.

Related source-of-truth documents:

- [Product requirements](../product/product_requirements.md)
- [Domain model](../domain/domain_model.md)
- [Business rules](../domain/business_rules.md)
- [Database design](../domain/database_design.md)
- [System architecture](system_architecture.md)

## 2. Scope

V1 API scope includes:

- Child Journey creation, reading, editing, and deletion;
- child profile reading and editing;
- Milestone Definition lookup for `CHILD` journeys;
- milestone create, read, update, and delete;
- memory create, read, update, and delete;
- media upload authorization, upload confirmation, ordering, reading, and deletion; and
- chronological timeline reading.

V1 API scope excludes:

- production authentication and account-management flows;
- production deployment, production domains, CDN, and cloud-provider choices;
- sharing, collaboration, comments, reactions, and social feeds;
- AI-generated content or media analysis;
- search, tags, albums, and advanced filters;
- non-child journey types; and
- payment or subscription APIs.

## 3. API conventions

### 3.1 Base path

All V1 endpoints should live under:

```text
/api/v1
```

V1 implementation targets local development first. The NestJS API should run locally, the mobile app should use a development base URL, PostgreSQL should run locally or in a local Docker environment, and object storage should use local MinIO. Production deployment details are intentionally deferred.

### 3.2 Transport and encoding

- Request and response bodies use JSON.
- Timestamps use ISO 8601 strings.
- Dates without time, such as `birthday`, use `YYYY-MM-DD`.
- IDs are UUID strings.
- `null` may be used for optional values that are intentionally absent.
- Empty strings should not be used as substitutes for `null`.

### 3.3 Naming

API fields use `camelCase`, even when database columns use `snake_case`.

Example:

```json
{
  "occurredAt": "2026-08-11T10:30:00.000Z",
  "createdAt": "2026-08-11T10:35:00.000Z"
}
```

### 3.4 Authentication placeholder

The data model includes `User -> Journey` ownership from the start, but production authentication is outside V1 product scope.

Until authentication is selected, implementation tasks must document the development-only identity strategy they use. The API contract must still be shaped as if ownership is enforced: clients must not be able to read or mutate another user's journey.

Client requests must not include `userId` when creating or mutating owned resources. The backend derives the current user from the authenticated identity or from the documented development-only identity strategy, then persists ownership internally.

### 3.5 Errors

Errors should use a consistent JSON shape:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Milestone occurredAt must not be in the future.",
    "details": {
      "field": "occurredAt"
    }
  }
}
```

Common status codes:

| Status | Meaning |
| --- | --- |
| `400` | Invalid request shape or invalid field value. |
| `401` | Missing or invalid identity when auth is enabled. |
| `403` | Identity exists but is not allowed to access the resource. |
| `404` | Resource does not exist or is outside the ownership boundary. |
| `409` | Request conflicts with current resource state. |
| `500` | Unexpected server error. |

For ownership-sensitive resources, returning `404` is preferred when revealing existence would leak another user's data.

## 4. Resource shapes

### 4.1 Journey

```json
{
  "id": "uuid",
  "type": "CHILD",
  "title": "Sophia's Little Steps",
  "description": null,
  "startDate": "2026-01-01",
  "endDate": null,
  "child": {
    "id": "uuid",
    "name": "Sophia",
    "birthday": "2026-01-01",
    "avatarUrl": null
  },
  "createdAt": "2026-08-11T10:00:00.000Z",
  "updatedAt": "2026-08-11T10:00:00.000Z"
}
```

`avatarUrl` is a temporary read URL generated by the backend. It is not the permanent storage reference.

### 4.2 Child

```json
{
  "id": "uuid",
  "journeyId": "uuid",
  "name": "Sophia",
  "birthday": "2026-01-01",
  "avatarUrl": null,
  "createdAt": "2026-08-11T10:00:00.000Z",
  "updatedAt": "2026-08-11T10:00:00.000Z"
}
```

### 4.3 Milestone Definition

```json
{
  "id": "uuid",
  "journeyType": "CHILD",
  "code": "FIRST_STEP",
  "defaultTitle": "First Step",
  "sortOrder": 30,
  "isActive": true
}
```

Definitions are read-only catalog data for the mobile app.

### 4.4 Milestone

```json
{
  "id": "uuid",
  "journeyId": "uuid",
  "milestoneDefinitionId": "uuid",
  "title": "First Step",
  "description": "She walked across the living room.",
  "occurredAt": "2026-08-11T10:30:00.000Z",
  "memories": [],
  "createdAt": "2026-08-11T10:35:00.000Z",
  "updatedAt": "2026-08-11T10:35:00.000Z"
}
```

`milestoneDefinitionId` may be `null` for a custom milestone. The milestone `title` is always required and remains editable.

### 4.5 Memory

```json
{
  "id": "uuid",
  "milestoneId": "uuid",
  "title": "Walking toward Grandma",
  "description": "Everyone started cheering.",
  "occurredAt": "2026-08-11T10:30:00.000Z",
  "media": [],
  "createdAt": "2026-08-11T10:36:00.000Z",
  "updatedAt": "2026-08-11T10:36:00.000Z"
}
```

### 4.6 Media

```json
{
  "id": "uuid",
  "memoryId": "uuid",
  "type": "VIDEO",
  "url": "https://temporary-read-url.example",
  "mimeType": "video/mp4",
  "fileName": "first-step.mp4",
  "fileSize": 7340032,
  "width": 1920,
  "height": 1080,
  "duration": 12.4,
  "sortOrder": 10,
  "createdAt": "2026-08-11T10:40:00.000Z",
  "updatedAt": "2026-08-11T10:40:00.000Z"
}
```

`url` is a temporary read URL. The backend persists a stable `storage_key`, but the API must not expose storage credentials or require the mobile app to store provider-specific permanent URLs.

## 5. Endpoints

### 5.1 Journeys

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/journeys` | Create a V1 Child Journey with its child profile. |
| `GET` | `/journeys` | List journeys owned by the current user. |
| `GET` | `/journeys/{journeyId}` | Get one journey and its child profile. |
| `PATCH` | `/journeys/{journeyId}` | Update journey title, description, start date, or end date. |
| `DELETE` | `/journeys/{journeyId}` | Delete the journey and dependent content. |

Create request:

```json
{
  "type": "CHILD",
  "title": "Sophia's Little Steps",
  "description": null,
  "startDate": "2026-01-01",
  "child": {
    "name": "Sophia",
    "birthday": "2026-01-01"
  }
}
```

Rules:

- The client must not send `userId`.
- The backend derives `user_id` from the current authenticated or development-only identity.
- `type` must be `CHILD` in V1.
- A child profile is required when creating a Child Journey.
- `birthday` must not be in the future.

### 5.2 Children

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/journeys/{journeyId}/child` | Get the child profile for a journey. |
| `PATCH` | `/journeys/{journeyId}/child` | Update child name, birthday, or avatar reference. |

Update request:

```json
{
  "name": "Sophia",
  "birthday": "2026-01-01",
  "avatarMediaUploadId": null
}
```

Avatar upload details may be handled through the same signed-upload mechanism as media, but avatar files are not Memory Media and must not appear in the timeline.

### 5.3 Milestone Definitions

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/milestone-definitions?journeyType=CHILD` | List active milestone suggestions for a journey type. |

Rules:

- V1 supports only `journeyType=CHILD`.
- Return definitions ordered by `sortOrder ASC`.
- Definitions are catalog suggestions, not user-created milestones.

### 5.4 Milestones

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/journeys/{journeyId}/milestones` | Create a milestone. |
| `GET` | `/journeys/{journeyId}/milestones` | List milestones in chronological order. |
| `GET` | `/milestones/{milestoneId}` | Get one milestone with memories and media. |
| `PATCH` | `/milestones/{milestoneId}` | Update milestone fields. |
| `DELETE` | `/milestones/{milestoneId}` | Delete milestone, memories, and media. |

Create request:

```json
{
  "milestoneDefinitionId": "uuid",
  "title": "First Step",
  "description": "She walked across the living room.",
  "occurredAt": "2026-08-11T10:30:00.000Z"
}
```

Rules:

- `milestoneDefinitionId` may be `null`.
- If present, the definition must apply to the journey's type.
- `title` and `occurredAt` are required.
- `occurredAt` must not be in the future.
- The default list order is `occurredAt ASC`.

### 5.5 Memories

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/milestones/{milestoneId}/memories` | Create a memory. |
| `GET` | `/milestones/{milestoneId}/memories` | List memories for a milestone. |
| `GET` | `/memories/{memoryId}` | Get one memory with media. |
| `PATCH` | `/memories/{memoryId}` | Update memory fields. |
| `DELETE` | `/memories/{memoryId}` | Delete memory and its media. |

Create request:

```json
{
  "title": "Walking toward Grandma",
  "description": "Everyone started cheering.",
  "occurredAt": "2026-08-11T10:30:00.000Z"
}
```

Rules:

- `title` and `occurredAt` are required.
- `description` is optional.
- A memory must remain within its original milestone.

### 5.6 Media upload and confirmation

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/memories/{memoryId}/media/uploads` | Request upload authorization. |
| `POST` | `/media/uploads/{uploadId}/confirm` | Confirm that direct upload completed. |
| `PATCH` | `/media/{mediaId}` | Update replaceable metadata when allowed. |
| `PATCH` | `/memories/{memoryId}/media-order` | Reorder media within one memory. |
| `DELETE` | `/media/{mediaId}` | Delete one media item and its object-storage file. |

Upload authorization request:

```json
{
  "type": "IMAGE",
  "mimeType": "image/jpeg",
  "fileName": "first-smile.jpg",
  "fileSize": 2457600,
  "width": 1600,
  "height": 1200,
  "duration": null
}
```

Upload authorization response:

```json
{
  "uploadId": "uuid",
  "uploadUrl": "https://temporary-upload-url.example",
  "method": "PUT",
  "headers": {
    "Content-Type": "image/jpeg"
  },
  "expiresAt": "2026-08-11T10:45:00.000Z"
}
```

Confirm upload request:

```json
{
  "sortOrder": 10
}
```

Confirm upload response:

```json
{
  "id": "uuid",
  "memoryId": "uuid",
  "type": "IMAGE",
  "url": "https://temporary-read-url.example",
  "mimeType": "image/jpeg",
  "fileName": "first-smile.jpg",
  "fileSize": 2457600,
  "width": 1600,
  "height": 1200,
  "duration": null,
  "sortOrder": 10,
  "createdAt": "2026-08-11T10:40:00.000Z",
  "updatedAt": "2026-08-11T10:40:00.000Z"
}
```

Media order request:

```json
{
  "items": [
    {
      "mediaId": "uuid",
      "sortOrder": 10
    },
    {
      "mediaId": "uuid",
      "sortOrder": 20
    }
  ]
}
```

Rules:

- The API generates the storage key.
- The mobile app uploads the binary directly to object storage with the signed upload URL.
- Media is not available until confirmation succeeds and metadata is persisted.
- Media can be reordered only within its own memory.
- `IMAGE` and `VIDEO` are the only V1 media types.
- The backend should remove abandoned uploads through implementation-specific cleanup.

### 5.7 Timeline

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/journeys/{journeyId}/timeline` | Get a client-ready chronological timeline. |

Timeline response:

```json
{
  "journey": {
    "id": "uuid",
    "type": "CHILD",
    "title": "Sophia's Little Steps"
  },
  "child": {
    "id": "uuid",
    "name": "Sophia",
    "birthday": "2026-01-01",
    "avatarUrl": null
  },
  "milestones": [
    {
      "id": "uuid",
      "milestoneDefinitionId": "uuid",
      "title": "First Step",
      "description": "She walked across the living room.",
      "occurredAt": "2026-08-11T10:30:00.000Z",
      "memories": [
        {
          "id": "uuid",
          "title": "Walking toward Grandma",
          "description": "Everyone started cheering.",
          "occurredAt": "2026-08-11T10:30:00.000Z",
          "media": []
        }
      ]
    }
  ]
}
```

Rules:

- Sort milestones by `occurredAt ASC`.
- Do not sort by `createdAt`, `updatedAt`, or IDs.
- Include only confirmed media.
- Include temporary read URLs when media is returned.

## 6. Validation rules

The API must enforce the business rules documented in [business_rules.md](../domain/business_rules.md). At minimum:

- Child `name` and `birthday` are required.
- Child `birthday` must not be in the future.
- Milestone `title` and `occurredAt` are required.
- Milestone `occurredAt` must not be in the future.
- A milestone definition must apply to the milestone's journey type.
- Memory `title` and `occurredAt` are required.
- Media must belong to exactly one memory.
- Media type must be `IMAGE` or `VIDEO`.
- Reordering media must not move media across memories.
- Deleting a parent must remove dependent database records and associated object-storage files.

## 7. Open decisions

The following details should be decided during implementation planning, not guessed silently:

- the development-only identity mechanism before production auth exists;
- pagination strategy for large timelines;
- maximum file sizes and accepted MIME types;
- signed URL expiration duration;
- whether media replacement uses `PATCH /media/{mediaId}` or a dedicated replacement endpoint; and
- exact cleanup policy for abandoned uploads.

Any decision that changes product behavior, ownership boundaries, or the media storage model should update this document and may require an ADR.
