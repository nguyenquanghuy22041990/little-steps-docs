# LittleSteps — System Architecture

## 1. Purpose

This document describes how LittleSteps V1 components collaborate to deliver a Child Journey. It defines system boundaries and data flows; detailed HTTP endpoints and payloads belong in [api_contract.md](api_contract.md).

The product and domain source of truth is documented in:

- [Product requirements](../product/product_requirements.md)
- [Domain model](../domain/domain_model.md)
- [Business rules](../domain/business_rules.md)
- [Database design](../domain/database_design.md)

## 2. V1 architecture overview

```text
┌──────────────────────┐
│ React Native mobile  │
│        app           │
└───────┬─────────┬────┘
        │         │
        │ API     │ Signed upload / read URL
        ▼         ▼
┌─────────────┐  ┌────────────────────────┐
│ NestJS API  │  │ S3-compatible storage  │
│             │  │ MinIO in local dev     │
└──────┬──────┘  └────────────────────────┘
       │
       │ SQL
       ▼
┌──────────────────────┐
│      PostgreSQL      │
└──────────────────────┘
```

The mobile application communicates with the backend for product data and authorization. It uploads large media files directly to object storage using short-lived signed URLs generated by the backend.

V1 implementation targets local development first:

- NestJS API runs locally.
- PostgreSQL runs locally or in a local Docker environment.
- Object storage uses MinIO locally.
- The mobile app connects to the local API through a development base URL.
- Production domains, CDN, deployment pipeline, and cloud-provider choices are deferred.

## 3. Component responsibilities

### 3.1 React Native mobile app

The mobile app owns the user experience:

- displaying the Child Journey timeline;
- collecting child, milestone, memory, and media input;
- requesting data and mutations from the API;
- requesting upload authorization and uploading media directly to object storage; and
- rendering usable read URLs returned by the API.

The mobile app must not connect directly to PostgreSQL. It must not contain object-storage credentials or treat a storage-provider URL as permanent data.

### 3.2 NestJS API

The API is the domain and security boundary. It owns:

- validating product and business rules;
- enforcing journey ownership when authentication and authorization are introduced;
- reading and writing PostgreSQL records;
- serving Journey, Milestone, Memory, Media, and Milestone Definition data to the mobile app;
- generating object-storage keys and short-lived signed upload/read URLs; and
- coordinating database and object-storage cleanup for deletion.

The API must not proxy large image or video uploads during the normal upload flow.

### 3.3 PostgreSQL

PostgreSQL is the system of record for structured product data:

```text
users
journeys
children
milestone_definitions
milestones
memories
media
```

It stores ownership, relationships, titles, descriptions, event times, ordering values, and media metadata. It does not store image or video bytes.

### 3.4 S3-compatible object storage

Object storage holds the binary content for child avatars, photos, and videos.

Use MinIO for local development. Production may later use an S3-compatible provider such as Amazon S3 or Cloudflare R2 without changing the product-facing data model.

The stable reference is a `storage_key`. Signed URLs are temporary transport mechanisms, not persistent domain data.

### 3.5 Milestone Definition catalog

Milestone Definitions are catalog data stored in PostgreSQL and returned through the API. The mobile app uses them to present appropriate suggestions for a Journey type.

For V1, only definitions applicable to `CHILD` journeys are available. A selected definition may prefill a title but does not prevent the user from editing it or creating a custom milestone.

## 4. Backend module boundaries

The initial backend should organize code by domain responsibility rather than by screen:

| Module | Responsibility |
| --- | --- |
| Users | User identity and journey ownership data. Authentication delivery is deferred. |
| Journeys | Journey lifecycle and Child Journey ownership boundary. |
| Children | Child-profile lifecycle. |
| Milestone Definitions | Read-only catalog lookup for suggested milestones. |
| Milestones | Milestone lifecycle and timeline ordering. |
| Memories | Memory lifecycle within a milestone. |
| Media | Media metadata lifecycle and direct-upload confirmation. |
| Storage | S3-compatible signed URL generation and object cleanup. |

Modules may depend on shared infrastructure such as the database client and storage adapter, but domain rules must not be duplicated across the mobile client and backend modules.

## 5. Primary data flows

### 5.1 Create a Child Journey

```text
Mobile app
  -> API: create Journey and Child profile
  -> PostgreSQL: persist Journey and Child
  <- API: return created journey data
```

The API validates that the created journey is a V1 `CHILD` journey and that its Child profile meets the business rules.

The mobile app does not send `user_id` when creating a journey. The API derives ownership from the current authenticated or documented development-only identity and persists `journeys.user_id` internally.

### 5.2 Browse the timeline

```text
Mobile app
  -> API: request a Journey timeline
  -> PostgreSQL: read Journey, Milestones, Memories, and Media metadata
  -> Storage: generate temporary read URLs when media is returned
  <- API: return chronological, client-ready timeline data
```

The API sorts milestones by `occurred_at` in ascending order. It never delegates database access or URL signing to the mobile app.

### 5.3 Add a milestone from a suggestion or custom input

```text
Mobile app
  -> API: create Milestone with optional definition reference
  -> API: validate the definition applies to the Journey type
  -> PostgreSQL: persist Milestone
  <- API: return created milestone
```

A milestone without a definition is custom. The API persists the milestone title as entered or confirmed by the user; it does not depend on dynamically resolving a catalog title later.

### 5.4 Upload media directly

```text
Mobile app
  -> API: request upload authorization with intended memory and file metadata
  -> API: validate ownership and generate storage key + signed upload URL
  <- API: return upload authorization

Mobile app
  -> Object storage: upload binary directly with signed URL

Mobile app
  -> API: confirm completed upload
  -> API: verify the uploaded object as required
  -> PostgreSQL: persist Media metadata and storage key
  <- API: return available Media record
```

The backend must only expose confirmed media as available. Failed or abandoned uploads must not appear in the timeline.

### 5.5 Delete media-backed content

```text
Mobile app
  -> API: request deletion
  -> API: validate ownership and determine dependent media
  -> Object storage: remove media objects
  -> PostgreSQL: remove metadata and dependent records
  <- API: report success or a recoverable failure
```

Database cascades help maintain relational integrity, but they cannot remove external objects. The backend must handle partial failures safely and avoid reporting a completed deletion when storage cleanup failed.

## 6. Ownership and authentication boundary

The data model includes `User -> Journey` ownership from the start. Authentication and account-management UI are not V1 product scope.

The specific V1 development authentication mechanism is intentionally undecided. It must not change the ownership model or create an API shape that exposes another user's journey. Before a production authentication approach is selected, backend implementation should use an explicit development-only identity strategy documented with the implementation task.

## 7. Cross-cutting rules

- PostgreSQL is the source of truth for structured entities and relationships.
- Object storage is the source of truth for media bytes only.
- The API is the sole authority that issues storage keys and signed URLs.
- A mobile client never receives permanent storage credentials.
- Real-world event time (`occurred_at`) and database record time (`created_at`/`updated_at`) remain distinct.
- API responses may contain temporary media URLs, but persistence stores only `storage_key`.
- A change to core ownership, media-upload, or Milestone Definition behavior requires an ADR and related-document updates.

## 8. Explicitly deferred architecture

V1 does not require:

- a web client;
- sharing or multi-user collaboration;
- background processing, transcoding, thumbnails, or notification jobs;
- search indexing, analytics pipeline, or AI pipeline;
- CDN configuration, production domains, deployment pipeline, or a production cloud-provider choice;
- a second Journey type or its Milestone Definition catalog.

Do not add these components unless a later product requirement and architecture decision introduce them.
